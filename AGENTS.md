## Единый регламент работы с карточками задач

Эти правила дополняют, но **не отменяют** более строгие ограничения проекта. В независимом репозитории хранятся актуальные файлы задач, центральная навигация VS Code служит указателем.

1. **Задача:** выбрать карточку `Задачи/00-Все-задачи.md` либо создать новую; указать цели, границы и критерии выполнения.
2. **План и согласование:** ДО диагностики оборудования и исправлений представить пошаговый план и дождаться одобрения пользователя. Допустимо читать только необходимые документы для составления плана.
3. **Диагностика:** после согласования плана — преимущественно read-only; не считать старые отчёты актуальным состоянием.
4. **Исправление:** backup, минимальные изменения, разрешения на каждый опасный production-шаг; без обхода ограничений прав или скрытых перезагрузок.
5. **Проверка и закрепление:** зафиксировать измеримый результат, подтверждающие источники, rollback и следующий шаг в `02-Ход-работы.md`.
6. **GitHub:** проверить diff, отсутствие секретов, отправить commit/push только в отдельную ветку своего проекта, при необходимости Draft PR; merge/force-push без разрешения запрещены.

**Продолжение:** в новом чате Codex открыть `03-Продолжить-в-Codex.md` конкретной задачи. Чат ChatGPT сам не синхронизируется с историей Codex; неподтверждённые сведения помечать явно.

## Обязательный GitHub completion gate — технические задачи

Правило действует для всех нетривиальных технических задач и изменений: диагностика и обслуживание Home Assistant, Proxmox, OpenWrt, сетей, VPN, серверов, контейнеров, MCP, кода, инфраструктуры и автоматизаций. Оно действует независимо от того, где выполнялась работа: ChatGPT, Codex CLI/Cloud, VS Code, MCP, SSH, терминал или веб-интерфейс.

1. **До начала:** определить правильный независимый репозиторий и карточку задачи; проверить ветку, git status, относящиеся документы и текущее состояние. Если карточки нет — создать её. Не затирать пользовательские или незакоммиченные изменения.
2. **По ходу работы:** после каждого существенного этапа обновлять журнал задачи. Фиксировать дату, источник доказательства, исходное состояние, значимые команды и операции, изменённые файлы/сервисы, исполнителя (ассистент или пользователь), резервную копию, способ отката, проверки и их фактический результат.
3. **Атрибуция:** если пользователь сам выполнил команды и прислал вывод, записывать это как «выполнено пользователем; подтверждено предоставленным выводом». Не приписывать ассистенту действия, которых он не выполнял. Отделять факт, вывод и предположение.
4. **Завершение:** обновить карточку и журнал (02-Ход-работы.md или эквивалент), а также CURRENT_STATE.md, changelog или README, если это необходимо для продолжения работы. Сохранять сжатые проверяемые результаты, а не стенограммы чата или огромные сырые логи.
5. **Публикация:** проверить git diff, staged diff и отсутствие секретов; сделать commit и push в отдельную ветку соответствующего репозитория. Для существенных изменений открыть Draft PR и приложить ссылки/commit SHA к отчёту. Не выполнять merge, force-push или reset без отдельного явного разрешения.
6. **Критерий DONE:** задачу можно назвать полностью завершённой только после проверки результата и публикации соответствующей документации/изменений в GitHub. В финальном отчёте указать репозиторий, ветку, commit SHA и PR (если создан).
7. **Если публикация невозможна:** из-за отсутствия доступа, инструмента, разрешения или прямого запрета пользователя — не заявлять, что фиксация выполнена. Пометить задачу как NOT SYNCED / BLOCKED — GitHub publication pending, перечислить, что осталось опубликовать, и не закрывать задачу как полностью завершённую.
8. **Безопасность:** не помещать в GitHub пароли, токены, приватные ключи, cookie, auth stores, приватные URL, персональные данные, сырые production-логи, базы и резервные копии. Сохранять только очищенные команды, метаданные и достаточные доказательства. Не публиковать изменения, если проверка на секреты не пройдена.

Это правило относится к значимым техническим действиям и результатам, а не к каждой отдельной команде как самостоятельному коммиту. Связанные операции группировать в логические этапы. История чата не является журналом проекта и автоматически в GitHub не синхронизируется.
