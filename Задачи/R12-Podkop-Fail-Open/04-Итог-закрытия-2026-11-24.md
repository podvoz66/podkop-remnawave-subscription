# R12 — итог закрытия диагностики VM202 (24.11.2026)

**Статус:** `PARTIALLY VALIDATED / OPERATIONALLY RESTORED`.

Этот документ фиксирует заключительную серию проверок production VM202 после LAB-этапа native updater. Он дополняет план и журнал работ, но не заменяет предыдущие доказательства LAB203/204.

## Краткий итог

- sing-box автоматически восстановился через procd после двух отдельных контролируемых SIGKILL: один в T1 и один в T2.
- На последнем подтверждённом снимке procd показывал `running=true`, PID `15536`, исполняемый файл `/usr/bin/sing-box`.
- Два свежих Clash delay-запроса прошли: `main-2-out=165 ms`, `USA-2-out=202 ms`.
- С Windows-клиента подтверждены DNS UDP, DNS TCP и HTTPS в штатном режиме.
- Полный terminal fail-open после исчерпания respawn budget и фактический DIRECT egress LAN-клиента во время отказа **не доказаны**.
- Диагностический этап закрыт по решению владельца. Повторные fault injection и изменения production не планируются.

## T1 — одиночный crash и procd respawn

Перед воздействием сверены PID `26560`, `/usr/bin/sing-box`, `starttime=11653603` и соответствующий procd instance.

Выполнен ровно один `SIGKILL`:

- старый PID: `26560`;
- новый PID: `10309`;
- respawn: примерно через 10 секунд;
- DNS-запрос и router-origin проверка адреса LAN-интерфейса прошли;
- VPN HTTPS-проверка с роутера завершилась ошибкой (wget RC=4); в журналах были VLESS/urltest timeouts.

Важно: проверка HTTPS с самого роутера к адресу `192.168.0.1` не является проверкой HTTPS с независимого LAN-клиента. Поэтому T1 не доказывает восстановление LAN-клиентского трафика. Повторный SIGKILL не выполнялся.

## T2 — проверка поведения после следующего crash

Перед воздействием PID `10309` был повторно сопоставлен с исполняемым файлом и procd.

Выполнен ровно один дополнительный `SIGKILL`.

Через примерно 1 секунду запрос `ubus service list` показал `running=false`. Первоначальный сценарий классифицировал это как `instance.fail`, однако такой одиночный снимок не доказывает окончательное исчерпание respawn budget: это могло быть краткое окно между завершением старого процесса и повторным запуском.

Последующая read-only проверка обнаружила новый PID `15536`. Следовательно:

- автоматический запуск нового процесса после T2 наблюдался;
- окончательный `instance.fail` не подтверждён;
- terminal fail-open и исчерпание лимита повторов не проверены;
- дополнительных SIGKILL не выполнялось.

## Стабильность восстановленного процесса

24.11.2026, около 21:57 (+05:00), сделаны три read-only снимка с интервалом 5 секунд:

| Параметр | Все три снимка |
|---|---|
| procd | `running=true` |
| PID | `15536` |
| Число процессов sing-box | 1 |
| EXE | `/usr/bin/sing-box` |
| Состояние процесса | `S` |
| `START_TICKS` | `15012167` |

PID и starttime не менялись на протяжении окна наблюдения около 15 секунд.

В журналах при этом присутствовали VLESS `context deadline exceeded` и HTTP/2 `INTERNAL_ERROR`. В 21:55:59 URLTest переключился с `main-7-out` на `main-2-out`. Это сетевые ошибки отдельных соединений, а не доказательство падения процесса.

## Clash API и VPN-ноды

- В конфигурации указан Clash API listener `192.168.0.1:9090`.
- Запрос к `127.0.0.1:9090` не прошёл; запрос к `192.168.0.1:9090` вернул данные API.
- Отсутствие утилиты `ss` в OpenWrt не позволило подтвердить listener через неё.
- Выбранные группы: `main-urltest-out → main-2-out`, `USA-urltest-out → USA-2-out`.
- Свежие delay-проверки через `https://www.gstatic.com/generate_204` вернули:
  - `main-2-out: 165 ms`;
  - `USA-2-out: 202 ms`.
- История API содержала соответствующие свежие timestamps: `2026-11-24T17:03:26Z` и `2026-11-24T17:03:27Z`.

Ранее выведенное `alive=false` не используется как критерий отказа: диагностический jq-вывод применял `// false`, а поле не было независимо проверено. Свежие delay-ответы подтверждают доступность проверки задержки, но не заменяют полноценный тест передачи данных через каждый outbound.

## Проверки с Windows LAN-клиента

Владелец выполнил:

- DNS UDP через `192.168.0.1`: ответ получен (`openwrt.org → 64.226.122.113`);
- DNS TCP через `192.168.0.1`: ответ получен;
- `curl.exe -I https://openwrt.org`: `HTTP 200`.

Это подтверждает штатную работу DNS и HTTPS с LAN-клиента в момент проверки. Это **не** доказывает DIRECT fail-open во время отказа sing-box.

Запрос к ChatGPT с ограничением скорости:

```text
HTTP=200
REMOTE=198.18.0.101
TIME=25.008039s
307200 bytes received
curl exit code 28 (max-time)
```

Адрес `198.18.0.101` относится к FakeIP-диапазону, поэтому запрос попал в механизм FakeIP/Podkop. Ответ HTTP 200 и полученные 300 KiB подтверждают начало передачи данных, но запрос завершился по 25-секундному лимиту. Это не полная успешная загрузка.

Мониторинг `/connections` был запущен после завершения клиентского запроса и не зафиксировал соединение. Поэтому конкретная цепочка outbound для этого запроса не установлена.

## Что не доказано

1. Переход в `instance.fail` после полного исчерпания procd respawn budget.
2. Реальный DIRECT egress LAN-клиента в момент terminal fail-open.
3. Полная передача данных через ChatGPT и точная outbound-цепочка этого запроса.
4. Независимое восстановление VM202 на уровне PVE/ядра/загрузки. Наличие открытой serial-консоли само по себе не является доказательством испытанного host-level recovery.

Маршрут роутера `default via 188.226.97.1 dev eth1` — это router-origin маршрут и сам по себе не доказывает DIRECT для LAN-клиентов.

## Воздействия и безопасность production

В заключительной серии T1/T2 были выполнены ровно два намеренных воздействия: по одному `SIGKILL` на каждый этап. Повторных SIGKILL не было. Podkop вручную не перезапускался; конфигурация, firewall, policy routing, подписки и ключи в рамках этой серии не менялись.

Последнее подтверждённое runtime-состояние: sing-box PID `15536`, procd `running=true`, выбранные выходы `main-2-out` и `USA-2-out`. Это исторический снимок на момент проверки, а не гарантия текущего состояния.

## Решение о закрытии

По решению владельца дальнейшие диагностические и аварийные испытания R12 прекращены из-за несоразмерных затрат времени и риска для рабочей инфраструктуры.

- **R12 status:** `CLOSED — PARTIALLY VALIDATED / OPERATIONALLY RESTORED`.
- Не заявлять полный fail-open PASS.
- Не повторять SIGKILL и не запускать новые fault/reboot tests.
- Не выполнять автоматические рестарты, обновления или изменения конфигурации в рамках закрытого R12.
- Сохранить текущую рабочую конфигурацию и существующие резервные копии.
- Этот итоговый документ фиксирует подтверждённые факты и оставшиеся ограничения; production rollout новых R12 guards не подразумевается.
